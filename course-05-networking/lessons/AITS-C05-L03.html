Learning objective

Choose diagnostic steps that test a hypothesis.

Explanation

First establish safety, authorization, affected users, services, start time and recent changes. Ask whether all sites fail or one application fails. Observe link and connection state safely. Read the client’s address, prefix, gateway and DNS configuration before changing it. Compare a known-good device on the relevant network.

On an authorized test device, basic diagnostics can include ipconfig /all, a gateway reachability test and nslookup for an approved test name. A ping timeout is evidence, not proof that a device is offline: filtering or policy may block replies. If gateway and external connectivity appear available but name resolution fails, investigate the configured resolver and related policy. Change one authorized variable at a time, record before/after results and preserve a rollback route.

Synthetic example

Synthetic outage: all clients reach the gateway; an approved external TCP test succeeds; lookups through the configured resolver time out. This supports a DNS-path hypothesis, not a confirmed broken cable.

Practical exercise

Choose the next two read-only checks and explain what each result would tell you.

Model response

Compare resolver configuration with the approved baseline and test the configured resolver from another affected client. Record results and escalate before changing settings.

Summary

Define scope and recent changes Observe before changing A failed ping is not a complete diagnosis
